代码不再昂贵之后：AI 时代软件工程的主要矛盾

发表于 2026-10-09
  • Aki's Memory
首页 AG99

当代码生成成本趋近于零后，软件工程的核心开始从 “构建系统” 转向 “控制系统熵”。

# 1. 问题的变化

过去几十年，软件工程一直在追求降低开发成本。

从高级语言、框架、组件化、云服务、低代码平台，到今天的 AI Coding，本质上都在试图减少工程师把想法转化为可运行系统所需要付出的劳动。

大语言模型出现之后，这个趋势第一次发生了质变。

过去，自动化工具主要是在局部提升效率：补全代码、生成模板、封装基础设施、减少重复劳动。而今天，AI 已经可以直接生成相当大比例的业务代码、脚本、测试、配置、文档，甚至可以参与重构、调试和系统设计。

这意味着一个新问题出现了：

当 “写代码” 不再昂贵之后，软件工程真正困难的部分还剩下什么？

这个问题比 “AI 会不会替代程序员” 更重要。

因为它讨论的不是某个职业是否消失，而是软件工程的主要矛盾是否正在变化。

# 2. 《没有银弹》在 AI 时代为什么重新成立

Fred Brooks 在《没有银弹》中提出过一个重要区分：软件复杂性可以分为偶然复杂性和本质复杂性。

偶然复杂性来自工具、语言、环境、流程、语法、样板代码等外部因素。它们并不属于问题本身，只是软件开发过程中的附加负担。

本质复杂性则来自问题本身。比如业务规则、状态空间、系统边界、人的协作、需求变化、异常路径、长期演化等。

AI Coding 的价值首先体现在它确实大幅降低了偶然复杂性。

它可以快速完成：

  • 样板代码
  • CRUD 接口
  • API 调用
  • 配置文件
  • 文档检索
  • 简单重构
  • 测试用例草稿
  • 常见错误修复

这些能力是真实的，不应该被低估。

但问题在于，AI 并没有消灭软件工程的本质复杂性。

相反，当代码生成变得便宜之后，那些过去被 “写代码很费劲” 掩盖的问题，会更加清晰地暴露出来。

例如：

  • 系统状态如何保持一致
  • 权限边界如何定义
  • 生命周期如何管理
  • 多模块之间如何协同演化
  • 异常路径如何被观测和恢复
  • 复杂业务规则如何避免相互冲突
  • 长期维护中如何防止系统腐化

也就是说，AI 降低的是 “生产代码” 的成本，而不是 “理解系统” 和 “控制系统” 的成本。

# 3. Vibe Coding：最高阶的代码复用

从这个角度看，vibe coding 不应该被简单理解为 “随便让 AI 写代码”。

它更准确的本质是：

Vibe coding 是 AI 时代最高阶的代码复用。

传统代码复用通常发生在几个层级：

  • 函数复用：复用一段确定逻辑
  • 库复用：复用通用能力
  • 框架复用：复用架构范式
  • 模板复用：复用项目骨架
  • 最佳实践复用：复用某类问题的成熟解法

而 vibe coding 复用的不是某个明确的函数、库或框架，而是大语言模型从海量代码、文档、issue、架构讨论和工程实践中压缩出来的模式。

它复用的是一种更抽象的东西：

人类软件工程经验的概率分布。

这也是为什么 vibe coding 在很多场景下会显得非常强大。

当一个需求落在常见问题空间中时，AI 往往可以迅速生成一套 “看起来就像成熟工程师会写出来” 的方案。它并不是凭空创造，而是在复用大量相似问题中的结构、命名、分层、接口、测试方式和错误处理习惯。

从这个意义上说，AI Coding 并不是普通的自动补全，而是一种跨项目、跨框架、跨语言、跨组织经验的高阶复用机制。

但复用层级越高，验证成本也越高。

函数复用要验证的是：

这段逻辑对不对？

框架复用要验证的是：

这个框架适不适合？

而 vibe coding 要验证的是：

AI 复用出来的这套隐含工程判断，是否真的适配当前系统？

这正是它的危险之处。

AI 可能复用出一个在大多数项目里都合理的结构，但这个结构未必符合当前系统的历史包袱、权限模型、状态约束、性能边界和团队习惯。

所以 vibe coding 的价值不在于让工程师不再判断，而在于把工程师的判断位置向上移动。

工程师不再只是逐行生产代码，而是在判断：

  • 这个抽象是否成立
  • 这个边界是否正确
  • 这个状态模型是否可靠
  • 这个复用模式是否适配当前上下文
  • 这个生成结果是否会增加系统长期熵

因此，vibe coding 越强，软件工程就越需要验证、约束和治理。

这也进一步说明：AI 并没有让软件工程消失，而是把软件工程从 “代码生产” 推向了 “高阶复用的控制”。

# 4. 从《人月神话》到 Agent 时代

《人月神话》讨论的是一个经典问题：

为什么增加人手不能线性提高软件开发效率？

Brooks 的答案是：软件工程不是简单的体力劳动叠加。随着人数增加，沟通成本、协调成本、接口成本、认知成本会快速上升。

在 AI 时代，这个问题出现了新的版本。

当系统中不再只有人类工程师，而是出现大量 AI Agent、自动化 Worker、工具链、执行器、调度器时，“人月神话” 并没有消失，只是对象发生了变化。

新的问题变成了：

Agent 数量增加为什么不能线性提高系统能力？

原因同样在于复杂性。

多 Agent 系统会带来新的沟通成本：

  • context pollution：上下文被无关信息污染
  • memory inconsistency：不同 Agent 记忆不一致
  • tool conflict：多个 Agent 调用工具时产生冲突
  • hidden dependency：任务之间存在隐式依赖
  • state divergence：各执行单元对系统状态的理解逐渐分叉
  • responsibility ambiguity：责任边界模糊，错误难以归因

这些问题本质上就是 Agent 时代的人月神话。

一个工程组织中，人越多，越需要架构、接口、流程和责任边界。

一个 Agent 系统中，Agent 越多，也越需要调度、权限、记忆、状态同步、观测和回滚机制。

所以 AI 并没有绕过《人月神话》。它只是把 “人和人之间的协作复杂性”，扩展成了 “人、Agent、工具、系统状态之间的协作复杂性”。

# 5. 软件正在从 “程序” 变成 “系统”

传统软件更像一个确定性的程序：

输入 → 处理 → 输出

虽然现实中的软件从来不完全简单，但大多数系统仍然可以被理解为一组相对稳定的逻辑、接口和状态转换。

而 AI Agent 系统更像一个动态系统。

它具有：

  • 长生命周期
  • 持续状态
  • 自主行为
  • 动态调度
  • 外部工具调用
  • 反馈循环
  • 多执行单元协作
  • 不完全可预测的输出

这使得 AI 时代的软件工程越来越接近控制论、系统论、调度论和信息论。

一个 Agent Framework 表面上看是在提供开发框架，实际上是在提供一套控制系统。

它的核心组件包括：

  • middleware：控制请求和执行链路
  • memory：控制信息的保留、遗忘和读取
  • orchestration：控制任务分解和协作顺序
  • scheduler：控制执行资源和优先级
  • event bus：控制事件传播和系统响应
  • lifecycle system：控制任务、会话、工具调用和 Agent 的生命周期
  • observability：控制系统是否可见、可诊断、可恢复

这些模块共同面对的核心问题是：

如何控制一个不断生成状态、不断改变自身、不断与外部交互的复杂系统？

这就是 “控制系统熵” 的含义。

这里的熵不是一个玄学隐喻，而是具体的工程现象：

  • 信息越来越多，但有效信息比例下降
  • 状态越来越多，但一致性越来越难保证
  • 自动化越来越强，但错误传播速度也越来越快
  • Agent 越来越多，但整体行为越来越难预测
  • 工具越接越多，但权限、依赖和副作用越来越难治理

当代码生成成本下降之后，系统熵就会成为更核心的问题。

# 6. AI 时代的软件工程核心能力

过去的软件工程重点是：

如何构建系统？

未来的软件工程重点会越来越变成：

如何控制复杂系统？

这并不是说编码能力不再重要，而是说编码能力会从核心瓶颈变成基础能力。

工程师真正重要的能力会更多转向：

  • 架构约束
  • 状态管理
  • 生命周期治理
  • 信息流控制
  • 权限边界设计
  • 可观测性建设
  • 高阶代码复用的验证
  • 复杂系统调度
  • Agent orchestration
  • 系统演化控制
  • 错误恢复和回滚机制

换句话说，AI 会让 “写出一段代码” 变得容易，但不会让 “构建一个长期稳定演化的系统” 变得容易。

软件工程的难点会从局部实现转向整体治理。

# 7. 结语

AI 并没有消灭软件工程。

它只是第一次真正暴露了一个事实：

软件工程真正困难的部分，从来都不是 “写代码” 本身。

写代码只是把复杂性表达出来。

真正困难的是理解复杂性、约束复杂性、组织复杂性，并让系统在长期演化中仍然保持可控。

因此，AI 时代的软件工程不会退化成简单的提示词工程。

相反，它会更加接近一种复杂系统控制工程。

当代码生成成本趋近于零，工程师的价值不再主要体现在 “我能不能写出这段代码”，而是体现在：

我能不能让一个由人、代码、Agent、工具、状态和反馈组成的系统持续处于可理解、可约束、可演化的状态。

这可能才是 AI 时代软件工程真正的主要矛盾。
